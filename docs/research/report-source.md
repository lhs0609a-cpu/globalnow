# Globalnow UX·UI 개선 연구 및 구현 보고서

2026-09-08 · 제품 운영자와 개발팀을 위한 코드 기반 감사

## 판단

가장 시급한 문제는 검색·카테고리가 실제 조회에 반영되지 않는 결함, 다음 페이지의 중복 요청과 목록 덮어쓰기, 저장 성공처럼 보이지만 다시 찾을 수 없는 흐름이었다. 색상 변경보다 사용자가 하려던 일을 끝내게 만드는 수정에 우선순위를 두었다. 첫 화면은 큰 세계 지도 중심에서 최신 뉴스 중심으로 재구성하고, 브리프·시장·저장·심층 탐색의 역할을 구분했다.

실제 이용 로그가 없으므로 현재 이탈률, 개선 후 이탈률, 1만 명 중 이탈 인원은 산출할 수 없다. 1만 명이라는 총 사용자 수만으로 동시 접속·요청량·서버 수용량을 계산할 수도 없다. 아래의 위험도는 발견한 기능 결함과 사용자 과업에 대한 정성적 우선순위이며 관측 이탈 확률이 아니다.

## 범위와 방법

한국어 뉴스·시장 대시보드를 처음 방문하는 사용자와 반복 방문자를 대상으로, 검색 → 주제 선택 → 기사 원문/해설 → 저장 → 재방문 흐름을 우선 검토했다. 전체 화면의 공통 셸·디자인 토큰·모바일 메뉴와 설정·인증·리포트·행사·관심 종목·예측·감성·출처 화면의 코드도 점검했다. 코드 점검과 자동 브라우저 검사는 실제 사용자 인터뷰나 운영 부하 시험을 대체하지 않는다.

연구 계획은 코드·정보구조 조사, W3C·React·Next·web.dev 및 NN/G 직접 연구 탐색, 반례와 한계 확인, 결함 우선순위화, 구현, 타입·빌드·브라우저 검증 순서였다. 계획 도구는 이 세션에 제공되지 않아 문서와 진행 메시지로 관리했다. 접근성/정보구조와 성능/측정은 딥리서치 지침에 따라 두 독립 연구로 분담하고, 핵심 원문을 조정자가 재열람했다.

## 디자인 결정의 근거

관련 정보를 한 화면에서 비교할 수 있게 묶되 모든 정보를 접지는 않는다. NN/G의 13명 정성 연구는 과도한 여백·분산·접힘이 데스크톱 탐색과 기억 부담을 늘릴 수 있음을 보여 준다. 뉴스 화면에 직접 측정한 개선율은 아니므로 레이아웃 결정의 근거로만 사용했다. [NN/G, The Negative Impact of Mobile-First Web Design on Desktop](https://www.nngroup.com/articles/content-dispersion/)

복잡한 앱에서는 주요 과업을 분명히 하고 보조 기능을 관련 맥락에서 접근할 수 있도록 배치한다. 이를 뉴스 중심 홈, 선택형 지도·커뮤니티, 고정 저장 메뉴에 적용했다. [NN/G, 8 Design Guidelines for Complex Applications](https://www.nngroup.com/articles/complex-application-design/)

검색 중·결과 수·실패는 짧은 상태 영역에 알리고 결과 목록 전체를 실시간 낭독하지 않는다. 일반 콘텐츠는 320 CSS px에서도 재배치되도록 검사하며, 표·지도 자체의 2차원 관계에 필요한 스크롤 예외를 모든 컨트롤로 확대하지 않는다. [W3C, Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html), [W3C, Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

주요 조작은 44px를 프로젝트 편의 목표로 삼았다. WCAG 2.2 AA의 최소 타깃 기준은 예외를 포함한 24×24 CSS px이며, 44px가 AA의 보편적 의무라는 뜻은 아니다. 포커스 표시·본문 바로가기·고정 영역에 의한 가림도 함께 검사해야 한다. [W3C, WCAG 2.2 Recommendation](https://www.w3.org/TR/WCAG22/)

검색·폼 컨트롤에는 목적을 설명하는 레이블을 제공한다. 초기 로그인 진입의 실패는 브라우저 alert 대신 화면 안 오류와 홈 복귀 경로로 전달한다. [W3C, Labeling Controls](https://www.w3.org/WAI/tutorials/forms/labels/)

Effect 기반 데이터 조회에서는 응답 역전·재마운트·중복 요청을 직접 다뤄야 한다. 이번 구현은 현재 의존성에 맞춰 요청 취소, 페이지 성공 후 확정, 공통 read-only 요청 처리를 적용했다. [React, useEffect: Fetching data](https://react.dev/reference/react/useEffect#fetching-data-with-effects)

## 1만 사용자와 이탈률의 측정 설계

누적 가입자 1만 명, 하루 방문자 1만 명, 동시 활성 사용자 1만 명은 서로 다른 조건이다. 이번 검증은 로컬 기능·레이아웃 검사이며 실제 1만 명 부하 시험을 수행했다고 볼 수 없다.

부하 시나리오 예시: 같은 순간 활성 탭 1,000개가 각각 120초마다 한 API를 조회하면 평균 약 8.3요청/초다. 10,000개라면 약 83.3요청/초다. 이는 A/T 산술 예시이고 재시도·초기 접속 급증·탭 수·외부 수집·다중 인스턴스는 포함하지 않는다. 이번 시장 위젯은 자동 갱신을 사용자가 선택하며 숨겨진 탭에서는 주기 요청을 생략한다.

GA4의 반송률은 비참여 세션 비율이며, 기사 원문을 빠르게 열고 나간 성공적인 과업도 시간만 보면 짧은 세션이다. 이 서비스의 핵심 과업 전환과 반송률을 별도로 보아야 한다. [Google Analytics, Engagement rate and bounce rate](https://support.google.com/analytics/answer/12195621?hl=en)

구현한 globalnow:analytics 브라우저 이벤트는 공급자 중립 연결 지점이다. 검색 원문·사용자 식별자·외부 전송은 넣지 않았다. page_view, search_submit, filter_change, feed_loaded, feed_error, search_empty, retry, outbound_open, bookmark_success, analysis_open을 제공한다. 운영 수집기·세션 정의·중복 제거·저장 시도 이벤트·성능 RUM 연동은 별도 필요하며 현재 분석 데이터가 수집·저장되고 있다는 뜻은 아니다.

성능 목표는 실사용 페이지뷰 p75 기준 LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하로 둔다. 기기·경로별로 분리해 관찰하고 로컬 자동 검사만으로 이 기준을 달성했다고 주장하지 않는다. [web.dev, Core Web Vitals thresholds](https://web.dev/articles/defining-core-web-vitals-thresholds), [web.dev, Lab and field data differences](https://web.dev/articles/lab-and-field-data-differences)

실험은 검색·저장 결함을 양쪽에 공통 수정한 다음 정보구조·카드 밀도를 비교한다. 신규/재방문, 모바일/데스크톱을 나누고 핵심 과업 완료율·오류·성능을 함께 본다. 필요한 표본 수는 실제 기준 전환율·검출할 최소 개선폭·유의수준을 정한 후 계산한다. 사용자 1만 명이면 자동으로 통계적 결론이 난다고 가정하지 않는다.

## 검증 범위

타입 검사, 전체 소스 린트, 프로덕션 빌드와 브라우저 회귀 검사를 실행한다. 브라우저 검사는 고정된 API 응답으로 검색·필터·페이지네이션·오류 복구·저장 유지·메뉴·대화상자를 확인하며 외부 API의 현재 가용성을 검증하는 시험은 아니다. 화면 검사는 320, 390, 768, 1024, 1440px 및 두 테마를 대상으로 한다. 실제 검사 결과는 동봉 검증 기록에 구분한다.

## 실행한 검증 결과

2026-09-08 로컬 Windows 환경에서 Next.js 16.1.6 프로덕션 빌드와 빌드 내 TypeScript 검사가 통과했다. 정적 페이지 53개를 생성했다. 전체 ESLint 검사는 오류 0건, 경고 10건이며, 경고에는 기존 예측·감성 화면의 미사용 변수와 관심 종목 컴포넌트의 Hook 의존성 항목이 포함된다.

Playwright Chromium 시나리오 9개에서 검색·카테고리·뒤로가기, 페이지별 단일 요청과 이전 목록 보존, 빈 결과와 오류의 분리, 게스트 저장·새로고침·CSV·해제, 모바일 해설의 재시도와 포커스 복귀, 전체 메뉴, 반응형·접근성, 늦은 응답의 덮어쓰기 방지, 연구 보고서의 제목·출처 링크·표·가로 넘침을 확인했다. 반응형 검사는 320·390·768·1024·1440px와 두 테마에서 수행했다. axe 자동 검사 범위는 홈의 390·1440px와 두 테마이며 지정한 WCAG A/AA 태그의 위반 0건이었다. 이는 전체 사이트의 WCAG 적합성 인증이나 수동 스크린리더 검사를 의미하지 않는다.

실제 캐시 모듈 검사는 동일 키 100개 동시 요청의 조회 1회 공유, 재조회 캐시, 삭제, 만료, 실패 후 복구, 200개 항목 상한을 통과했다. RSS ID 안정성과 샘플 검색·필터의 의미도 확인했다. 단일 프로세스 함수 검증이며 100명 또는 1만 명의 실제 접속 부하 시험이 아니다.

최종 Playwright 결과는 9 passed, 종료 코드 0이었다. 이 Windows 환경에서는 테스트가 끝난 뒤 임시 서버 종료가 지연되어 해당 실행에서 생성한 Next 서버 프로세스를 직접 종료했다. 이후 테스트 러너가 결과 파일을 생성하고 정상 종료했다.

밝은 모바일 홈과 어두운 데스크톱 홈의 전체 페이지 캡처, 보고서 상단을 직접 시각 점검했다. 화면 캡처는 고정된 테스트 기사 응답을 사용했다. 운영 외부 API·실제 인증 계정의 DB 권한·개인별 격리·실측 Web Vitals와 이탈률은 검증하지 않았다. 재현 명령과 자동 검사 구성은 저장소 README와 tests/ux.spec.ts에 기록했다.

## 근거의 공백과 조사 종료 판단

검색은 W3C 상태 메시지·reflow·타깃·폼, NN/G 복잡 앱·정보 분산 반례, web.dev 실험실/실사용 차이·CWV, React 경쟁 상태, Next 캐시, GA4 세션 정의로 제한했다. 각 주장의 원문과 적용 범위를 확인했고 출처가 열리지 않은 SWR 자료는 확정 근거에서 제외했다. 더 많은 일반 UX 글보다 제품의 실제 과업 관찰과 운영 데이터가 다음 결정을 바꿀 가능성이 높아 일반 문헌 탐색을 종료했다.

접근성·요청 취소는 원문 근거와 코드 관찰이 일치해 신뢰가 높다. 뉴스 우선 레이아웃의 상대 우월성은 합리적인 설계 가설이며 이 제품의 사용자 실험으로 확정되지 않았다. 이탈률 개선폭과 1만 동접 수용 여부는 근거가 없으므로 수치 결론을 보류한다.
